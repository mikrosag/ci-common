# ci-common

Shared CI/CD infrastructure for repos in the `mikrosag` org. There is one self-hosted GitHub Actions runner (a `LaunchDaemon` on Frans's Mac, registered at the **org** level, default runner group → automatically available to every repo in `mikrosag`, no per-repo runner setup needed).

## What lives here

- `.github/workflows/security-checks.yml` — reusable workflow (`workflow_call`): `gitleaks` secret scanning + `semgrep` SAST. Call it from any repo's `pull_request`-triggered CI:
  ```yaml
  jobs:
    security:
      uses: mikrosag/ci-common/.github/workflows/security-checks.yml@main
  ```
- `.github/workflows/dynamic-tests-nix.yml` — reusable workflow: runs a repo's test suite inside a Nix devShell (`nix develop -c <test-command>`), for reproducible/hermetic dependency pinning. Requires the calling repo to have its own `flake.nix` (see `templates/nix-test/`).
- `.github/workflows/dynamic-tests-container.yml` — reusable workflow: builds `Dockerfile.test` and runs the test suite inside the resulting container via OrbStack/Docker. For repos that already ship as containers (see `templates/orbstack-test/`).
- `.github/workflows/sca-scan.yml` — reusable workflow: `osv-scanner` dependency/SCA scan (free, OSS, Google). Call from any repo's CI. **Observability-only (`continue-on-error: true`)** — surfaces findings in every PR's logs but doesn't block merges yet, since severity data is inconsistent across ecosystems and there's no triaged baseline. Needs a manifest (`requirements.txt`, `package.json`, etc.) to scan — a repo with deps declared only in `flake.nix` should also keep a `requirements.txt` mirror (see `automation/requirements.txt`) purely so this has something real to check.
- `.github/workflows/container-scan.yml` — reusable workflow: builds a Dockerfile and scans the image with `trivy`, failing on CRITICAL/HIGH by default. Only relevant for repos that build a container.
- `.github/workflows/lint-js.yml` — reusable workflow: `npm ci` + ESLint, for JavaScript/TypeScript repos (see `templates/lint-js/`).
- `.github/workflows/mcp-server-security-gate.yml` — reusable workflow: the fail-closed admission gate for onboarding a new MCP server onto `mcp-gateway`. Chains `security-checks.yml` + `sca-scan.yml` + `container-scan.yml` with two MCP-specific jobs: `rules-and-policy` (MCP semgrep rules — prompt-injection-shaped tool descriptions, unrestricted filesystem paths, unsanitized shell-out, overly broad scopes, see `semgrep-rules/mcp-server.yml` — plus `conftest` against `policy/mcp-server-compose.rego` and `policy/mcp-server-manifest.rego`, the latter also covering the runtime egress-allowlist requirement), and `sbom-sign` (Syft SBOM + keyless `cosign sign-blob`). `rules-and-policy` was two jobs (`mcp-semgrep-rules` + `policy-check`) until 2026-08-13; they did identical setup — checkout, App-token mint, ci-common checkout — so merging halved that per gate run. See `templates/mcp-server-registry/` for how to wire a calling repo's `ci.yml`, and `homelab/mcp-gateway/registry/README.md` for the manifest schema and the `gateway-sync` flow this gate feeds into. Requires `cosign`/`syft`/`conftest` on the runner (added to `mac-config`'s pipeline-critical Homebrew list).
- `templates/launchd-deploy/` — for repos that ship as scheduled launchd jobs on the Mac (the `automation` repo is the reference implementation of this).
- `templates/orbstack-deploy/` — for repos that ship as a container via OrbStack on the Mac.
- `templates/nix-test/`, `templates/orbstack-test/` — scaffolding for the two dynamic-test reusable workflows above.
- `templates/lint-js/` — scaffolding for `lint-js.yml`.

## Org-wide conventions (apply to every repo, not just this one)

- **Branch protection:** `main` is PR-gated, no direct pushes. CI (`pull_request` trigger) must pass before merge. `deploy.yml` (`push` to `main` trigger) runs only after merge.
- **Runner:** all repos `runs-on: [self-hosted, macOS]` — same physical runner serves the whole org via the default runner group.
- **Dynamic tests run against mocked externals, not live services.** Unit-test pure/parseable logic; mock network, email, browser, subprocess. See `automation/tests/` for worked examples.
- **Nix is installed on the runner Mac but its profile script isn't auto-sourced in non-interactive shells.** Every `run:` step using `nix` must first do `echo "/nix/var/nix/profiles/default/bin" >> "$GITHUB_PATH"` (already handled inside `dynamic-tests-nix.yml` — only relevant if you're writing a new workflow that uses Nix directly).
- **Nix flakes only see git-tracked/staged files.** New `flake.nix` or test files must be `git add`ed before `nix develop` works, even before committing.
- **Deploy logic stays per-repo** (different repos deploy to different places — launchd vs. OrbStack), but should start from the matching template here rather than being designed from scratch.
- **`ruff`, `osv-scanner`, `trivy` are installed via Homebrew on the runner Mac** (not containerized), same pattern as `gitleaks`/`semgrep`. If any goes missing: `brew install ruff osv-scanner trivy`.
- **Snyk, Aqua (platform), and similar paid SaaS scanners are deliberately not used.** Free/OSS equivalents cover the same ground: `osv-scanner` for SCA, `trivy` for container images, `semgrep`+`gitleaks` for SAST/secrets. Don't add a paid tool without a clear reason it's not covered.
- **There is no pipeline failure notification, by design.** A `notify-telegram.yml` reusable workflow used to exist and was called with `if: failure()` from every deploy workflow. It never delivered a single message: its `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` came from org-level secrets, which on this org's Free plan are unavailable to private repos, so both resolved empty — and its `curl` had no `--fail`, so the job reported success anyway. Removed 2026-08-10 rather than repaired: Frans does not want Telegram notifications for CI. Check run status via the GitHub UI or `gh run list`. **Don't re-add a notifier without asking.**
- **Org-level Actions secrets do not work in this org.** Free plan + private repos means every `${{ secrets.* }}` sourced from org scope resolves to an empty string, silently. Use repo-level secrets (`gh secret set ... --repo mikrosag/<repo>`); see `mcp-spotlight-facts/AGENTS.md` for the worked example.
- **Agent instructions:** every repo should have its own `AGENTS.md` (canonical) with tool-specific stubs (`CLAUDE.md`, `GEMINI.md`, etc.) — see `automation/AGENTS.md` for the pattern. This repo only carries `AGENTS.md` + `CLAUDE.md` since it's infra that's edited rarely; replicate the fuller stub set in repos that get frequent day-to-day edits.

## Kanban (Linear) — team `MIK`

- **Tracking lives in Linear:** one team, **`Mikrosag` (key `MIK`)**, covering all five `mikrosag` repos. Workflow states are unchanged from the old convention: `Backlog → Todo → In Progress → In Review → Done`, plus Linear's defaults `Canceled` and `Duplicate`. One team rather than one per repo — five teams is admin overhead with no benefit at this scale, and Linear's free tier caps at 2 teams / 250 issues, so a single team leaves headroom.
- **Repo scoping is a label, not a link:** every issue carries exactly one repo label — `homelab`, `automation`, `ci-common`, `mac-config`, `mcp-gateway`. They sit under a **`repo` label group**, which is what makes "exactly one" an enforced constraint rather than a convention: Linear allows only one label from a group per issue. This is deliberately what fixes the old setup's coverage gap: the `mikrosag Roadmap` GitHub Project was linked to only `automation` and `ci-common`, because Projects v2 items are repo-linked and adding a repo was fiddly enough that it never happened. Labels aren't repo-linked, so there is no reason to leave a repo out.
- **GitHub integration is connected to all 5 repos** (Linear → Settings → Integrations → GitHub). It gives three things for free:
  - branches and PRs auto-link to their issue,
  - PR state (open / draft / merged) shows on the Linear issue,
  - **a PR containing a magic word (`Fixes MIK-123`, `Closes MIK-123`) auto-transitions the issue to `Done` when it merges to `main`.** That removes the manual status flip the old flow needed on every card.
- **Requirements live in the issue, not in a second system.** Linear issue descriptions take full markdown, attachments and sub-issues, so a card's problem statement / context / proposed approach / open questions go straight into the description — written by Frans, or drafted by an agent as an intake step (agent asks clarifying questions, drafts the structured description, Frans confirms, agent creates the issue via the Linear MCP). There is no `Spec:` line and no second document to keep in sync.
- **Multi-issue initiatives get a Linear Project** — an overview doc plus its own set of issues — rather than a standalone write-up elsewhere. Keeps the narrative in the same system as the work it describes.
- **Notion is reference material only, and is not part of the per-card flow.** It keeps durable, cross-cutting content that outlives any single card: architecture decisions, environment/inventory reference, standing narratives that inform many future tickets. The `mikrosag Use Cases` database is **retired for new entries** — existing entries stay as historical reference. Never check Notion as a step in working a card, and never mirror status into it.
- **Agents talk to Linear over the official Linear MCP server** (hosted by Linear), not `gh` or Projects v2 GraphQL. This is very likely the real fix for the old coverage gap — Projects v2 has no clean field-update API, so moving a card's Status programmatically was awkward enough that automation never got built and the project never got extended past two repos.
- **Card → code flow:** pick up an issue in Linear (assigned to you, or from `Backlog`/`Todo` carrying your repo's label) → read the description in full, plus any sub-issues → move it to `In Progress` (Linear MCP `update_issue`, or in-app) → branch (Linear's suggested branch name is fine as-is) → PR with `Fixes MIK-123` in the body → CI runs the usual checks → merge → `deploy.yml` deploys and Linear marks the issue `Done` automatically.
- **Assignment is the `service` label. Nothing writes the assignee field — not agents, not `main`.** Every issue carries exactly one label from a `service` label group (one child per fleet agent) alongside its `repo` label, and Linear enforces the exactly-one, so an agent's board is exactly `repo = homelab AND service = <its id>`. **Unrouted work is handed over with a transient `triage` label, and nothing ever writes the assignee field.** Frans labels a card `triage`; `main` reads it, sets the `repo`/`service` labels, and removes `triage` — so the intake queue is exactly `label = triage`. The assignee field is deliberately *not* the queue: in Linear, assigned-to-Frans means Frans owes an action, and using his own inbox as the fleet's work queue inverts the meaning of every card in it. Agents must not write the field at all, because they authenticate to Linear **as Frans** — an agent "assigning itself" actually assigns him. On 2026-09-10 sixty cards carried `assignee: Frans Sauermann` set exactly that way, a field that read like ownership while carrying none; all 60 were cleared.
- **Making the agents Linear members looks free and is not.** Linear's Free plan allows unlimited members, so inviting one account per agent passes a shallow cost check. But Linear bills **every member seat** on paid plans (guests included), and Free caps the workspace at **250 non-archived issues** — `Done` and `Canceled` count, only archiving removes them. With the fleet filing ~29 cards a night, that cap is days away, not months. Twenty seats would turn a ~$20/month Basic upgrade into ~$200/month. The label is the permanent answer.
- **CI enforces the card, and the closing keyword.** `linear-card-check.yml` fails any PR whose body does not close a MIK card, and separately calls out a body that *mentions* `MIK-123` with no closing keyword — that links the card but never transitions it, which is the silent half-failure worth naming. Exemptions are a `no-card` label (a visible, attributable act on the PR) and fork PRs (an outside contributor has no access to this workspace). This exists because on one night twelve PRs landed and only three carried a `Fixes` line; the other nine were invisible to the board while this same convention forbids moving status by hand.
- **The old GitHub Project is archived, not deleted.** [`mikrosag Roadmap`](https://github.com/orgs/mikrosag/projects/1) remains read-only as the historical record of everything already `Done`, and any cards that were in flight at cutover finish out there. **No new cards are created there.**

## Versioning

Callers should pin to a tag once this repo stabilizes (e.g. `@v1`) rather than `@main`, so a change here can't silently break every repo's CI at once. Currently early enough that everything points at `@main` — revisit once there's more than one consumer repo.
